# TILE_PLAN — 地形タイル分割案の検証（Phase 0）

検証スクリプト：`scripts/phase0_tile_plan.py`（既存OSMを読み取り専用で使用）／結果：`data/phase0/tile_plan_phase0.json`

## 1. 前提

- 対象：OSM公園境界（238,552m²）＋50m余白。範囲 x −186〜305m、y −404〜687m
- タイル格子はローカル原点に揃えた正方格子。ID形式 `t100_{i}_{j}`（例 `t100_-2_+6`）
- 地形の元データ：DEM1A（約1m格子）。公園の起伏は最大でも約8m（−2.4〜+5.8m）

## 2. 3案の比較（実測計算）

| タイル | 枚数 | うち公園にかかる | 1枚の三角形数（2m格子） | 全体（2m格子） | 評価 |
|---|---|---|---|---|---|
| 50m | 187 | 128 | 1,250 | 233,750 | ファイル数・リクエスト数が多すぎる |
| **100m** | **55** | **39** | **5,000** | **275,000** | **採用** |
| 200m | 18 | 14 | 20,000 | 360,000 | 読み込み単位が粗く、モバイルで不要部分まで読む |

## 3. 100mタイルを採用する理由

1. **55枚で全域をカバー**し、同時に読み込むのはカメラ周辺の3×3〜5×5枚で済む
2. 地形LODを段階的に用意できる：
   - LOD0：2m格子（5,000三角形）— 半径150m以内
   - LOD1：5m格子（800三角形）— 150〜400m
   - LOD2：10m格子（200三角形）— それより遠く（全55枚を常時表示しても11,000三角形）
3. 1m格子（20,000三角形／枚）は、平坦な公園ではほぼ見た目の差がないため使わない。DEM1Aは**サンプリング元**として使い、メッシュは2m格子に間引く
4. 起伏がほぼ平坦なので、タイル境界の段差は小さい。境界の頂点は両隣で**同じDEM値を共有**し、さらに**スカート**（境界から下に0.5m垂らす帯）を付けて、LOD差の隙間を隠す

## 4. タイルに入れないもの（独立管理）

| 資産 | 理由 |
|---|---|
| 木場公園大橋 | 長さ250mで3〜4タイルにまたがるため、単独のGLB |
| 建物 | 既存PLATEAU由来。建物単位で管理し、タイルIDだけ属性に持つ |
| 樹木・低木・草 | インスタンス配置JSON（タイル別に分割）で管理 |
| 物理コリジョン | 表示用と別の簡易形状。地形はRapierのheightfield（タイル単位） |

## 5. 1タイルに含めるもの

`terrain_{id}.glb` には：地形メッシュ（LOD0〜2）、園路面、広場面、水面（池・水路）。マテリアルは全タイル共通の数種類に限定し、テクスチャはタイル間で共有（KTX2）。

## 6. 容量の見積もり［推定］

| 項目 | 見積もり |
|---|---|
| 地形LOD0 1枚（位置＋法線＋UV、meshopt圧縮後） | 約40〜60KB |
| 全55枚（全LOD） | 約3〜5MB |
| 共有テクスチャ（地面・草・土・水、KTX2） | 約4〜8MB |
| 初回読み込み（周辺9枚＋遠景LOD2＋テクスチャ） | 約6〜10MB → 目標20〜40MBに十分収まる |

## 7. Phase 1で確認すること

- 2m格子と旧5m格子の見た目の比較（同じ地点のスクリーンショット）
- タイル境界をまたいで歩いたときの段差・隙間（自動テスト：境界上の高さ差 < 1cm）
- DEMの欠損（水面・建物下で最大15%）の補完方法：DEM5A → 周辺値の補間 → 水面は水位の標高で平面化
